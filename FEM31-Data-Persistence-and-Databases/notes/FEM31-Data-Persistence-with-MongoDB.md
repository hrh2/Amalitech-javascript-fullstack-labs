## 1. Why a database? (the problem FEM30 left)

FEM30's tasks lived in a JavaScript array. When the process stops, memory is freed and the data is gone; two server
processes wouldn't share it either. A **database** is a separate program whose job is to store data on disk safely, find it
quickly and let many clients use it at once. The API becomes **stateless** in the good sense: it keeps nothing important
in its own memory, so it can be restarted (or run several times) without losing data.

```
Client ──HTTP──► Express API (Node process) ──driver/ODM──► MongoDB server (mongod) ──► files on disk
                 routes + validation                         stores collections of documents
```

## 2. SQL vs NoSQL (Objective 1)

| | SQL (e.g. PostgreSQL) | NoSQL document store (e.g. MongoDB) |
|---|---|---|
| Data shape | **tables** of **rows** and **columns**, all rows have the same columns | **collections** of **documents** (JSON-like, BSON), documents can differ |
| Schema | defined up front, enforced by the database | flexible; structure enforced by your code (Mongoose) if you want it |
| Relationships | **foreign keys** + `JOIN` queries | **references** (an id stored in another document) or **embedding** (nested data) |
| Query language | SQL | JavaScript-style query objects (`{ completed: false }`) |
| Strengths | strong consistency, complex joins, reporting, transactions | easy to evolve, maps directly to JSON/JavaScript objects, quick to start |
| Typical choice when | data is highly relational (orders, payments, inventory) | data is document-shaped and changes often (profiles, content, catalogs) |

Terminology map: table ~ collection, row ~ document, column ~ field, primary key ~ `_id`, JOIN ~ `populate()` (done by
the application, not the database).

**Why MongoDB here:** the resource book uses it, its documents look like the JSON the API already sends, and Mongoose is
the matching ODM. **Prisma** is the equivalent for PostgreSQL: you write a `schema.prisma` file, run a migration to create
tables, and call a generated, typed client (`prisma.task.findMany()`). The concepts (schema, model, CRUD calls, async
queries, connection string) are the same; only the database and the tool differ.

## 3. MongoDB and Mongoose basics (Objectives 2 and 3)

- **MongoDB** stores **documents** in **collections** inside a **database**. Every document has a unique **`_id`**
  (an **ObjectId**: 12 bytes shown as 24 hex characters, e.g. `6adf74ebeb04d7025a8bbeb8`, generated by the driver, roughly
  increasing over time).
- **Mongoose** is an **ODM** (Object Data Modeling library) on top of the official MongoDB driver. It gives you:
  - a **Schema**: the fields, their types and rules (`required`, `trim`, `maxlength`, `unique`, `default`);
  - a **Model**: a class made from the schema that you use to query (`Task.find()`, `Task.create()`...), and whose
    instances are **documents** with `.save()`;
  - validation, casting (`"true"` -> `true`), defaults, timestamps, middleware and `populate`.
- **Connection string:** `mongodb://127.0.0.1:27017/task_api_dev` = protocol, host, port, **database name**. The database
  is created automatically on first write. Atlas strings look like `mongodb+srv://user:password@cluster.../db`; the password
  is a secret and belongs in `.env`, never in code or git (`.env` is in `.gitignore`, `.env.example` shows the format).
- **One connection per process.** `mongoose.connect()` is called once at start-up; every model uses it. Connecting takes
  time, so the server connects **first** and only then calls `listen`.
- Everything that touches the database is **asynchronous** (returns a Promise): use `await`.

## 4. The Blog challenge (`blog-db/`)

```
db.js            mongoose.connect(...) helper                           (task: "connection in a db.js file")
models/User.js   name, email                                            (task: "User Schema")
models/Post.js   title, content, author: { type: ObjectId, ref: 'User' } (task: "Post Schema, author references User")
blog.js, demo.js create user -> create post -> find + populate          (task: "write a script")
```

### The reference (the "crucial step")
```js
author: { type: mongoose.Schema.Types.ObjectId, ref: 'User', required: true }
```
The post does **not** contain the user. It stores the user's `_id`. `ref: 'User'` names the model that id belongs to.

### What `populate` does
```js
Post.findById(id)                              // author: "6adf7532c50d41cfc2a45288"  (just an id)
Post.findById(id).populate('author', 'name email')   // author: { _id, name, email }
```
`populate` runs a **second query** (`User.find({ _id: ... })`) and replaces the id with the document. MongoDB has no
server-side JOIN, so this is Mongoose doing it for you; the second argument picks which fields to bring back. The test
`populate` checks the raw document in the database really holds an ObjectId (`_bsontype === 'ObjectId'`) rather than an
embedded user. If the referenced user was deleted, `populate` gives `null` (tested) instead of throwing.

### Schema features used
- `email`: `required`, `unique: true` (creates a **unique index**: a duplicate gives MongoDB error code **11000**,
  even with different capitals, because `lowercase: true` normalises first), `trim`, `match` (format check).
- `timestamps: true` on posts: `createdAt` / `updatedAt` maintained by Mongoose.
- `postSchema.index({ author: 1 })`: an index so "all posts by this author" doesn't scan the whole collection.
- **Virtual populate** (bonus): `User.virtual('posts', { ref: 'Post', localField: '_id', foreignField: 'author' })` lets
  `User.findById(id).populate('posts')` return a user with their posts without storing a posts array in the user (the
  test confirms the stored user has no `posts` field). This is the one-to-many relationship the module's section 4
  ("Advanced Data Modeling") describes.
- **Reference vs embed:** embedding (putting posts inside the user document) is fast to read but duplicates data and can
  grow without limit; referencing keeps one copy and lets posts be queried alone. A blog's posts are many and
  independent, so reference.

### Running it
`npm start` in `blog-db/` prints each step: the created user (email lower-cased by the schema), the post with just the
author id, the same post found without and with `populate`, and a user with their posts. It **empties** the users and
posts collections of the `blog_demo` database first so that it can be re-run (it never touches other databases).

## 5. The CRUD API refactor (`task-api-db/`)

### Before and after
```js
// FEM30 store.js (memory)                       // FEM31 store.js (MongoDB)
get(id)    { return tasks.find(t => t.id === id); }      get(id) { return Task.findById(id); }
create(x)  { tasks.push({ id: nextId++, ... }); }        create(x) { return Task.create(x); }
remove(id) { tasks.splice(index, 1); }                   async remove(id) { (await Task.deleteOne({ _id: id })).deletedCount === 1 }
```
The function names and meanings stayed; only the inside changed. That is the **separation of concerns** payoff from
FEM30: routes (HTTP), validation, store (data). The routes changed only by adding `async`/`await`.

### CRUD -> Mongoose
| API | store function | Mongoose call |
|---|---|---|
| `GET /tasks`, `?completed=` | `list(filter)` | `Task.find({ completed }).sort({ _id: 1 })` |
| `GET /tasks/:id` | `get(id)` | `Task.findById(id)` (`null` if missing -> 404) |
| `POST /tasks` | `create(data)` | `Task.create(data)` |
| `PUT /tasks/:id` | `replace(id, data)` | `findById`, `task.set({ title, completed })`, `task.save()` |
| `PATCH /tasks/:id` | `update(id, changes)` | `findById`, `task.set(changes)`, `task.save()` |
| `DELETE /tasks/:id` | `remove(id)` | `Task.deleteOne({ _id })`, check `deletedCount` |

`replace`/`update` use find-then-save so that **schema validation and timestamps run** (`updatedAt` changes, `createdAt`
is kept; a test shows both). The alternative (`findByIdAndUpdate`) is one query but skips some of that unless
`runValidators` is set.

### The schema (`models/task.js`)
`title` required/trimmed/1-200 characters, `completed` Boolean default false, `timestamps: true`, an index on
`completed`, and a `toJSON` transform that renames `_id` to a string `id` and hides `__v` (Mongoose's internal version
counter) so the API's JSON contract stays `{ id, title, completed }` plus the two timestamps.

### What had to change because of MongoDB
- **Ids are ObjectId strings.** The `:id` validator now accepts exactly 24 hex characters and answers 400 otherwise.
  Without it, `GET /tasks/abc` makes Mongoose throw a `CastError`; with it that never reaches the database. I deliberately did
  **not** use `mongoose.isValidObjectId()`: it also accepts any 12-character string (`abcdefghijkl`), so a test
  checks that exact id returns 400.
- **Two layers of validation.** The API's `validateTask` gives friendly messages and covers shape problems (not an object,
  arrays). The **schema** is the last line of defence: a 201-character title passes the API check but the schema rejects it,
  and the error handler turns Mongoose's `ValidationError` into `400 { error: 'Validation failed', details: [...] }`
  (tested). `CastError` also maps to 400.
- **Express 5 + async:** a rejected promise from an async route handler is passed to the error handler automatically, so
  there is no `try/catch` in the routes. Database failures become `500 Internal Server Error` with a generic message and the
  real error (which may contain connection details) logged only on the server (a test checks a fake error containing a
  password never appears in the response).
- **Start-up order:** `server.js` connects first; if MongoDB is unreachable it prints
  `Could not connect to MongoDB (...)`, masks any `user:password@` in the URI, and exits with code 1. (`serverSelectionTimeoutMS: 5000`
  makes it fail in 5 s instead of the default 30 s.)
- **Configuration:** `MONGODB_URI` and `PORT` from the environment or an optional `.env` (loaded with Node's built-in
  `process.loadEnvFile()`, so no `dotenv` package).
- **Seeding:** `npm run seed` empties the `tasks` collection and inserts three samples (used by the tests too).

### Proof that it persists
1. `npm run seed`, `npm start`, `POST /tasks {"title":"Survive a restart"}` -> 201.
2. Stop the server (the process and its memory are gone), start it again, `GET /tasks` -> the new task is still listed
   (checked in a terminal; it is also an automated test that closes and reopens the connection).
3. `mongosh task_api_dev --eval 'db.tasks.find()'` shows the documents in the database itself.

## 6. Testing against a real database

- The tests use a **real MongoDB**, not mocks, because the things that matter (schema validation, indexes, ObjectId
  casting, `populate`) are behaviours of the database/ODM; a mock would only test that I mocked it correctly.
- **They must never touch real data**, so: a separate database `task_api_test` / `blog_test`; `test/setup.js` **throws** if
  the database name doesn't end in `_test` (a test deletes all tasks, so a wrong `MONGODB_URI` must be a hard error); and
  the database is **dropped** after the run (`after(() => dropDatabase())`).
- `--test-concurrency=1`: test files share one database, so files run one after another.
- Each test starts from the same three seed tasks via `store.reset()`. MongoDB generates new ids every time, so the tests
  look ids up by title instead of hard-coding them.
- 46 tests (`task-api-db`) cover everything FEM30 covered, adapted to ObjectIds, plus: persistence across a reconnect,
  schema defaults/trim, schema rejecting bad data when the API validation is bypassed, strict mode dropping unknown fields (also in
  the stored document), timestamps (`updatedAt` moves, `createdAt` doesn't), the `completed` index, malformed ids
  (including the 12-character trap), and 500s not leaking.
- 12 tests (`blog-db`): defaults and normalisation, unique-email error 11000, required fields, the stored `author` being an
  ObjectId reference, populate with and without field selection, deleted-author `null`, finds by author, virtual populate.

## 7. Common mistakes (and how these projects avoid them)

| Mistake | Symptom | Here |
|---|---|---|
| Forgetting `await` on a Mongoose call | you get a Query/Promise object (or nothing happens) | every store call is awaited; tests would fail |
| Connecting on every request | slow, connection leaks | one `connect()` at start-up |
| `listen` before the database is connected | early requests fail | connect first, then listen |
| Hard-coding the connection string/password | secrets in git | `MONGODB_URI` from env/`.env`, `.env` ignored, URI masked in logs |
| Trusting `isValidObjectId` | accepts 12-character strings | strict 24-hex regex |
| Passing a bad id to `findById` | `CastError` -> 500 | validated first (400), plus CastError mapped to 400 |
| Using `req.body` straight in `create` | clients set any field | validation copies known fields; schema strict mode drops the rest |
| Using the `_id`/`__v` fields as the API contract | leaks internals | `toJSON` transform |
| Running tests on your dev database | data loss | separate `_test` database + a hard guard + dropped after |
| Not populating, then reading `post.author.name` | `undefined` | `.populate('author')` |
| Duplicate-key errors surfacing as 500 | confusing | (users: unique email, code 11000 tested; the Task API has no unique fields) |
| `populate` on a field without `ref` | no effect/error | `ref: 'User'` set |
| Expecting JOIN-like atomic reads | stale data between the two queries | know that populate is two queries |
| Skipping `User.init()` in tests | unique index not built yet, duplicate test is flaky | `init()` awaited in `before` |

## 8. TA review questions

**1. SQL vs NoSQL: when would you choose each?** SQL for highly relational data needing joins/transactions/strict
schema (orders, payments); a document store for flexible, JSON-shaped, evolving data. Here a task or a blog post is one
self-contained document, so MongoDB fits.

**2. What are a collection, a document and `_id`?** A collection is a group of documents (like a table); a document is a
JSON-like record (like a row); `_id` is the unique primary key, an ObjectId unless you set it.

**3. What is Mongoose and why use it if MongoDB is schemaless?** An ODM: schemas, validation, defaults, casting,
populate and a convenient model API over the driver. MongoDB won't stop you storing garbage, so the schema keeps the
application's data consistent.

**4. Schema vs model vs document?** Schema = the blueprint (fields and rules). Model = the class compiled from it
(`Task`) used for queries. Document = one instance/record (`new Task(...)`, or a result of `find`).

**5. How do you connect, and where?** `mongoose.connect(uri)` once at start-up in `db.js`; models share that
connection. `server.js` waits for it before `listen`, and exits with a clear message if MongoDB is unreachable.

**6. How is a relationship modelled?** The Post stores the author's `_id` (`type: ObjectId, ref: 'User'`); `populate`
loads the user. For the reverse direction a **virtual** with `localField/foreignField` avoids storing an array.

**7. What does `populate` do under the hood?** A second query for the referenced documents, then it swaps ids for
documents in the result. It is not a database JOIN and isn't atomic.

**8. Reference or embed?** Reference when related data is large, grows, is shared, or needs separate queries (posts);
embed when it is small, always read with the parent and owned by it (an address in a profile).

**9. What changed in the Task API when you replaced the array?** `store.js` was rewritten with Mongoose (async), routes
got `await`, ids became ObjectId strings (new id validator), Mongoose errors were mapped to 400, a connection and
start-up check were added. The endpoints, status codes and error format stayed the same.

**10. Why does `findById` with `abc` need handling?** Mongoose can't cast it to an ObjectId and throws a `CastError`;
the API validates the id first (400) and also maps `CastError` to 400 as a safety net.

**11. Why not `mongoose.isValidObjectId`?** It returns true for any 12-character string. A strict 24-hex check is
safer (tested with `abcdefghijkl`).

**12. Two validation layers, why?** The API validator gives user-friendly responses and checks request shape; the schema
guarantees nothing invalid is ever stored, whatever code path writes. A title of 201 characters shows the schema
catching what the API check allows.

**13. How do PUT and PATCH map to Mongoose?** Both load the document and `set` + `save()` (so validation and timestamps run).
PUT sets all fields (missing `completed` resets to false); PATCH sets only the supplied ones.

**14. How do you prove data persists?** Create a task, stop and restart the server (and, in the automated test, disconnect and
reconnect), read it back; also inspect with `mongosh`.

**15. How do you keep tests from damaging real data?** Separate `_test` database, a guard that throws on any other name, and
dropping it afterwards.

**16. Why a real database in tests instead of mocks?** The behaviour under test (validation, indexes, casting,
`populate`, unique errors) lives in Mongoose/MongoDB; mocking it would test nothing real. The cost is needing a running
MongoDB (documented).

**17. What does `unique: true` really do?** Creates a unique **index** in MongoDB; it is not a validator. A duplicate
fails with `E11000` (code 11000) when written, which is why the test waits for `User.init()` to build the index first.

**18. How are secrets handled?** The URI comes from `MONGODB_URI` / `.env` (git-ignored, `.env.example` committed);
start-up errors mask `user:password@`; 500 responses never include driver messages.

**19. What would change with PostgreSQL + Prisma?** A `schema.prisma` with a `Task` model, a migration to create the table,
the generated `PrismaClient` in `store.js` (`prisma.task.findMany/create/update/delete`), integer or UUID ids instead of
ObjectIds, and SQL constraints instead of Mongoose validation. Routes, API validation and error handling would stay the same.

**20. Limitations?** Single local database, no auth, no pagination, no transactions, ids are not sequential, no
migrations (Mongoose doesn't need them, but index changes are applied on `init`), and the tests need a local MongoDB.
